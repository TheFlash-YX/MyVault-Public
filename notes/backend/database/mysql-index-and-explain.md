# 详细内容

## 最左前缀

- 假设普通 B-tree 联合索引 (a,b,c)，先按 a，再按相同 a 下的 b，再按相同 a/b 下的 c 排序。
- WHERE 条件书写顺序不要求与索引顺序一致；有使用条件不等于优化器必然选择索引。

| 条件 | 本轮示例中的范围定位 |
|---|---|
| a=1 AND b=2 AND c=3 | a,b,c |
| b=2 AND a=1 | a,b |
| c=3 AND a=1 | a，c 继续筛选 |
| b=2 | 不满足最左前缀 |
| a=1 AND b>2 AND c=3 | a,b，c 继续筛选 |
| a>1 AND b=2 AND c=3 | a，b/c 继续筛选 |

- 缺中间列不会抹掉已匹配的左侧前缀；不满足最左前缀也不能断言绝不扫描索引，实际计划可能存在索引扫描等路径。
- 上表针对这些具体条件，不把“范围以后全失效”推广到所有运算符和优化策略；更不能把无法用于范围定位等同于无法筛选。

## 回表、覆盖与 ICP

- InnoDB 二级索引包含主键值；所需列不全在索引中时，需要根据主键取得完整记录，称为回表。
- 覆盖索引：查询所需列全部在索引里；例如索引 (a,b,c) 支持 SELECT a,b,c WHERE a=1，只有 a 参与定位也可覆盖。
- ICP：需要回表时，将可下推条件先在索引记录上判断，减少不符合条件记录的回表。
- 索引 (user_id,status)，条件 user_id>100 AND status='已支付'：假设扫描 1000 条、其中 100 条符合 status，则候选回表量由 1000 降到 100，索引扫描量并未因此变成 100。
- 是否启用 ICP 取决于引擎和计划；示例不是一次实际数据库测量。

## EXPLAIN

| 字段 | 含义与误区 |
|---|---|
| type | const 常见于唯一键等值单行定位；ref 为非唯一等值访问；ALL 为全表扫描 |
| key | 计划选择的索引；NULL 表示未选择索引，不是看是否存在任何索引 |
| rows | 预估扫描行数，不是精确值或最终返回量 |
| Extra: Using index | 覆盖索引，不是泛指用了索引 |
| Extra: Using index condition | 索引条件下推 |
| Extra: Using where | 需要条件过滤，不代表索引失效 |

- EXPLAIN 展示计划；没有实际运行就不能说已测出性能提升。
- key 有索引名称但没有 Using index，仍可能利用索引定位后回表。

## 索引成本与多表查询

- 走索引不等于发生一次磁盘 I/O：页可能已缓存，也可能访问多个页。
- 小表或命中比例很高时全表扫描可能更便宜；SELECT * 命中 99 万/100 万行时，大量二级索引回表可能不划算。
- 覆盖索引能减少取列成本，但返回 99 万条记录仍有扫描和传输成本。
- 联查例：users.id 为主键，orders.user_id 上的索引帮助按用户查订单；再按 status 等值过滤可考虑 (user_id,status)。
- 若要读取 amount 且该列未被索引覆盖，仍需回表；追加 amount 会扩大索引并增加写维护成本，需按负载权衡。
- 排查顺序：看 EXPLAIN → 检查连接和过滤字段的索引 → 只取需要的列、评估覆盖 → 比较计划与实际耗时。
- 关注表的数据量和命中比例，不是简单按“表的数量”判断是否需要索引。
- 本轮尚未系统复习函数、隐式转换等索引使用限制，不将索引失效题标为完整掌握。
