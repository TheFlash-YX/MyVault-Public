# 退款系统场景面试复盘

## 一、场景背景

某电商平台有一套售后自动退款系统，主要处理服装品类退款。

业务规模与现状：

- 每天约 10 万笔售后单；
- 其中约 2 万笔符合自动退款条件；
- 单笔退款金额约 50～500 元；
- 系统可以读取订单状态、物流轨迹、历史客诉等信息；
- 对于系统无法判断或风险较高的订单，会转人工客服处理。

近期业务提出新需求：

> 有部分用户频繁退货、疑似“薅羊毛”，希望系统能够识别高风险用户，不能再把所有符合基础条件的订单都直接自动退款。

这道题表面上是在问“怎么设计退款规则”，实际上面试官一路追问的是一套完整的资金系统能力：

**业务规则 → 状态机 → 异常排查 → 幂等 → 支付一致性 → 对账 → 工程取舍**

---

# 二、问题一：如何设计退款判断逻辑

## 面试官问题

> 最近有些用户频繁退货、疑似薅羊毛，系统不能全部自动退款。你会怎么把这个需求落地成系统里的判断逻辑？

## 当时回答

> 当前系统可以读取订单状态、物流轨迹、历史客诉，可以从这三个维度给每个用户打分，设置一个阈值，低于这个阈值自动退款，超过这个阈值转人工处理。

## 回答中的问题

方向没有错，但问题在于**过早进入“评分模型”**。

退款系统中有很多条件并不是风险高低问题，而是硬性业务规则，例如：

- 订单未支付；
- 已经全额退款；
- 超出售后期限；
- 退款金额超过剩余可退金额；
- 订单状态不允许退款。

这些条件不应该进入评分模型，而应该直接判断。

因此更合理的结构应该是：

**硬规则 + 风险规则 + 风险评分 + 人工兜底**

## 更好的回答

可以这样回答：

> 我会把退款判断分成三层。  
> 第一层是退款资格校验，比如订单是否支付、是否已经退款、是否在售后期限内、剩余可退款金额是否足够，这些属于硬规则，不满足就直接拒绝。  
> 第二层是高风险硬规则，例如短时间内退款次数过多、退款率异常、同设备多账号、历史恶意退款记录等，命中后直接转人工。  
> 第三层再对剩余灰度用户做风险评分，可以综合订单状态、物流轨迹、历史客诉、退款频率、账号行为等信息。低风险自动退款，中高风险进入人工审核。  
> 这样可以避免单纯依靠评分模型导致一些明显异常订单被误放。

## 核心知识点

退款判断不要只设计一个：

```text
risk_score < threshold → 自动退款
```

更合理的是：

```text
退款请求
   ↓
退款资格校验
   ↓
是否满足硬性退款条件？
   ├─ 否 → 拒绝
   ↓ 是
高风险规则
   ↓
是否命中？
   ├─ 是 → 人工审核
   ↓ 否
风险评分
   ↓
低风险 → 自动退款
中风险 → 人工审核
高风险 → 拒绝 / 人工复核
```

可以考虑的风险特征：

- 最近 7/30 天退款次数；
- 最近 7/30 天退款金额；
- 历史退款率；
- 历史投诉记录；
- 是否签收；
- 是否高价值订单；
- 同 IP / 设备 / 地址关联多个账号；
- 同 SKU 集中退款；
- 新账号高频退款；
- 历史异常退款记录。

# 三、问题二：退款系统的状态机如何设计

## 面试官问题

> 确定判断逻辑以后，一笔售后单从进来到结束，在你的系统里会经过哪些核心状态？哪些状态之间的跳转是严格禁止的？

## 当时回答

> 打分前 → 打分后 → 低于阈值自动退款，超过阈值转人工。禁止从打分前直接进入人工客服或者直接退款。

## 回答中的问题

这里最大的概念问题是：

> **流程 ≠ 状态机**

“打分前、打分后、自动退款、人工处理”更接近业务流程，而状态机关注的是：

> 当前状态是什么 → 什么事件发生 → 是否允许进入下一个状态。

另外，“禁止从打分前直接进入人工”也不一定合理。

例如：

- 风控服务超时；
- 物流数据缺失；
- 系统判断异常；
- 高金额订单；
- 特定业务规则命中。

这些场景本来就可以直接转人工兜底。

## 更好的状态设计

可以设计为：

```text
CREATED
待处理

↓
CHECKING
资格与风险判断中

↓
AUTO_APPROVED / MANUAL_REVIEW
自动退款通过 / 人工审核

↓
REFUND_PROCESSING
退款处理中

↓
REFUND_SUCCESS / REFUND_FAILED / REFUND_UNKNOWN
退款成功 / 退款失败 / 退款状态未知
```

人工审核还可以有：

```text
MANUAL_REVIEW
   ↓
APPROVED / REJECTED
```

## 严格禁止的状态跳转

例如：

- `REFUND_SUCCESS → REFUND_PROCESSING`
- `REFUND_SUCCESS → 再次全额退款`
- `MANUAL_REVIEW → REFUND_PROCESSING`，但人工尚未审核通过
- 未调用支付渠道直接把状态修改为 `REFUND_SUCCESS`
- 已关闭的退款单重新进入处理中
- 已全额退款订单再次创建全额退款

## 核心知识点

状态机关注三个东西：

1. 当前状态；
2. 触发事件；
3. 合法状态迁移。

资金系统中状态机的核心作用是：

> **限制非法状态转换，防止重复退款、错退款和状态混乱。**

# 四、问题三：前端显示“退款已受理”，但后端没有记录，如何排查

## 面试官问题

> 系统上线后，有用户投诉说前端页面提示“退款已受理”，但订单系统里根本没有退款记录。日志没有明显报错，支付退款 API 也没被调用。你会怎么一步步缩小排查范围？

## 当时回答

> 把这笔订单的流程链路复现一遍，看看具体是哪个环节出错了。用户在前端发起退款请求 → 系统接收到退款请求事务 → 退款请求事务在系统中流转 → 退款结果写回数据库。

## 回答中的问题

方向是对的，但太泛。

因为题目已经提供了两个关键信息：

- 支付退款 API 没有调用；
- 后端没有退款记录。

这意味着问题大概率发生在：

```text
前端
↓
API 网关
↓
退款服务入口
↓
退款单创建
```

没必要优先检查支付后的流程。

更好的排查方式应该强调：

> **利用 request_id / trace_id / order_id 顺着调用链找到“断点”。**

## 更好的回答

可以这样说：

> 我会先确认前端“退款已受理”这个提示到底来自哪里，是前端本地直接展示、网关返回，还是退款服务真实返回。  
> 然后通过 order_id、request_id 或 trace_id 查询整条调用链，确认请求有没有真正进入退款服务。  
> 如果网关有日志但退款服务没有日志，说明问题在服务路由、RPC 或消息投递；如果退款服务已经收到请求但数据库没有退款单，就重点检查创建退款单的事务是否提交、是否发生回滚、异步消息是否发送成功。  
> 因为支付退款 API 根本没有调用，所以排查重点应该放在支付之前，不需要先检查支付侧。

## 推荐排查顺序

```text
1. 前端是否真实请求后端
      ↓
2. API 网关是否收到请求
      ↓
3. 退款服务是否收到请求
      ↓
4. 是否创建退款单
      ↓
5. 事务是否提交
      ↓
6. 是否进入后续异步流程
      ↓
7. 是否调用支付退款 API
```

## 可以补充的工程手段

- `trace_id`
- `request_id`
- `order_id`
- 分布式链路追踪
- API 网关日志
- 服务日志
- 数据库事务日志
- MQ 生产 / 消费日志
- 支付调用日志

# 五、问题四：支付已经退款，但接口超时，用户再次点击退款怎么办

## 面试官问题

> 如果退款 API 响应超时了，但实际上支付网关已经退款成功，此时系统没拿到结果，给前端返回“系统繁忙请重试”。用户马上再次点击退款，你的系统会发生什么？怎么防范？

## 当时回答

> 前端会发起多个退款请求到后端，可能导致多次退款事务发生。可以用 user_id + 订单 id 做幂等判断，一个用户对于一个订单只能有一个退款事务在流程中，后续发送到后端的请求都作废。

## 回答中做得好的地方

抓到了最关键的概念：

> **幂等**

这是正确方向。

## 回答中的问题

### 1. `user_id + order_id` 粒度过粗

一个订单可能存在：

- 部分退款；
- 分商品退款；
- 多次合法退款；
- 售后单维度退款。

因此不能简单认为：

> 一个订单只能有一个退款事务。

更合适的幂等标识是：

- `refund_request_id`
- `refund_order_id`
- `merchant_refund_no`
- 售后单 ID

### 2. 重复请求不应该简单“丢弃”

真正的幂等应该是：

> 相同业务请求执行一次，并且后续重复请求返回第一次请求对应的状态或结果。

例如：

```text
第一次请求：
refund_id = R123
状态 = PROCESSING
```

第二次请求再次到达时：

```text
发现 R123 已存在
→ 不再发起第二次支付退款
→ 返回 PROCESSING
```

如果已经成功：

```text
→ 直接返回 REFUND_SUCCESS
```

### 3. 没有抓住最核心的一点：超时 ≠ 失败

支付系统中：

> **接口超时不能直接认为业务失败。**

可能出现：

```text
退款系统
   ↓
支付网关
   ↓
实际退款成功
   ↓
返回响应
   X 网络超时
退款系统没收到
```

此时系统真实状态其实是：

> UNKNOWN

而不是：

> FAILED

## 更好的回答

> 首先退款请求必须具备业务幂等性，每次退款创建一个唯一的 refund_id 或 merchant_refund_no，并通过数据库唯一约束保证同一个退款请求只能创建一次。  
> 调用支付平台时也携带同一个退款单号。用户重复点击时，如果本地已经存在退款单，则不再发起新的支付退款，而是直接返回已有退款单的状态。  
> 另外，支付接口超时不能直接标记为失败，因为支付渠道可能已经执行成功。此时应该把退款状态标记为 UNKNOWN 或 PROCESSING，然后使用 refund_id 主动向支付渠道查单，最终确认是 SUCCESS 还是 FAILED。

## 推荐流程

```text
创建 refund_id
      ↓
数据库创建退款单（唯一约束）
      ↓
REFUND_PROCESSING
      ↓
调用支付网关
      ↓
┌──────────┬──────────┬──────────┐
成功        明确失败      超时
↓           ↓            ↓
SUCCESS     FAILED       UNKNOWN
                           ↓
                        主动查单
                           ↓
                  SUCCESS / FAILED
```

# 六、问题五：月底对账发现退款金额对不上，第一步怎么查

## 面试官问题

> 财务团队月底对账，发现系统记录的自动退款总金额和实际支付网关支出的退款总金额对不上。面对这个情况，你第一步会怎么查？

## 当时回答

> 每笔退款记录都有幂等 id，先缩小范围，把能对上的自动退款记录和实际支付网关支出的记录排除，再看哪些记录对不上，然后根据具体情况进一步排查。

## 回答中做得好的地方

方向是正确的：

> 逐笔匹配 → 找出差异单 → 分类处理。

这已经具备基本对账意识。

## 回答中的问题

缺少最重要的第一步：

> **先确认双方统计口径是否一致。**

很多“对不上”并不是系统真的丢钱，而是统计口径不同。

例如：

系统按：

> 退款创建时间

支付平台按：

> 退款完成时间

就可能出现：

```text
9 月 30 日 23:59 创建退款
10 月 1 日 00:01 支付成功
```

月度统计自然会出现差异。

## 更好的回答

> 我第一步不会马上逐笔查订单，而是先确认系统和支付平台的对账口径是否一致，包括时间范围、退款成功状态定义、统计时间字段、币种、手续费、部分退款等。  
> 口径确认一致之后，再通过 merchant_refund_no 或 refund_id 做逐笔匹配，把双方都存在且金额一致的记录排除，只保留差异单。  
> 最后把差异单分类，比如本地成功但渠道无记录、渠道成功但本地无记录、金额不一致、重复退款、状态不一致，再针对不同类型进行自动修复或人工处理。

## 对账差异类型

```text
A. 本地成功 / 渠道成功
   → 正常

B. 本地成功 / 渠道无记录
   → 重点排查

C. 本地无记录 / 渠道成功
   → 可能本地状态丢失

D. 本地金额 ≠ 渠道金额
   → 金额异常

E. 同一个 refund_id 出现多笔渠道记录
   → 可能重复退款

F. 状态不一致
   → 需要查单修复
```

## 核心知识点

对账一般可以理解为：

```text
统一口径
   ↓
逐笔匹配
   ↓
生成差异单
   ↓
差异分类
   ↓
自动修复 / 人工处理
```

# 七、问题六：项目排期紧，只能保留三项能力，砍哪一项

## 面试官问题

> 项目排期被严重压缩，只有两周，必须砍掉一个能力。风控规则、状态机、防重试幂等和对账机制只能保留三个，你第一刀砍哪一块？砍掉后如何利用客服团队或简单业务规则低成本兜底？

## 当时回答

> 会砍掉风控规则，因为后三者与系统的财务合理性高度相关，在我这里出入账出现问题是绝对的红线。如果砍后三个需求，不仅会导致资金流转问题，还会导致用户体验下降。对于自动退款订单，可以筛选出秒退货的用户，让客服去复核是什么问题，在一定程度上降低退款率。

## 回答中做得好的地方

这道题整体回答不错。

你已经意识到了：

- 状态机；
- 幂等；
- 对账；

本质上属于：

> **资金正确性能力**

而风控更多是：

> **降低业务损失能力**

资金系统上线时，优先级通常应该是：

```text
Correctness > Efficiency
```

也就是：

> 钱不能退错、不能多退、出了问题必须能追回和核对。

## 可以继续优化的地方

不要直接说：

> “砍掉风控。”

因为业务场景本身明确要求解决薅羊毛。

更成熟的做法是：

> **砍复杂风控体系，保留基础硬规则。**

例如暂时不上完整评分模型，只保留：

- 7 天退款次数 ≥ 3 → 人工；
- 高金额退款 → 人工；
- 历史恶意账号 → 人工；
- 异常物流状态 → 人工；
- 其他满足基础条件的订单 → 自动退款。

这样：

> 状态机 + 幂等 + 对账

正常建设。

同时：

> 复杂风险评分模型延期。

## 更好的回答

> 如果只能砍一个，我会砍复杂的风控评分体系，但不会完全取消风控。状态机、幂等和对账直接关系到资金正确性，不能牺牲。  
> 风控部分可以先降级成几个简单高收益规则，比如高频退款、高金额退款、历史恶意用户直接转人工，剩余用户继续自动退款。复杂的风险评分、设备关联、模型策略后续再迭代。这样既能按期上线，又能通过人工客服兜住高风险用户。

# 八、这场面试暴露出的主要问题

## 1. 容易过早抽象

例如第一题直接想到：

> 打分 + 阈值。

第四题直接想到：

> user_id + order_id 幂等。

问题不是这些方案完全错误，而是没有先定义：

> **业务不变量**

退款系统最重要的不变量应该是：

```text
不能多退
不能错退
不能超过可退金额
不能漏记退款状态
不能把 UNKNOWN 当 FAILED
退款结果必须可追踪
资金最终必须能够对账
```

系统设计应该围绕这些不变量展开。

---

## 2. 知道概念，但没有准确说出关键术语

这轮面试中已经涉及：

- 状态机；
- 幂等；
- 对账。

但如果能主动说出下面这些词，技术深度会明显提升：

- 硬规则；
- 风险评分；
- 人工兜底；
- 终态；
- 非法状态转换；
- trace_id；
- refund_id；
- merchant_refund_no；
- UNKNOWN 状态；
- 主动查单；
- 幂等返回；
- 数据库唯一约束；
- 最终一致性；
- 对账口径；
- 差异单。

---

## 3. 回答结构不够稳定

很多回答是：

> “我会……然后……再……”

容易显得比较散。

建议以后固定使用：

## 原则 → 方案 → 异常兜底

例如支付超时问题：

### 原则

> 超时不能认为失败，退款必须具备幂等性。

### 方案

> 每次退款创建唯一 refund_id，本地先创建退款单，再携带同一个 refund_id 调用支付平台；重复请求返回同一笔退款状态。

### 异常兜底

> 支付接口超时进入 UNKNOWN 状态，通过 refund_id 主动查单，最终更新为 SUCCESS 或 FAILED。

这种回答通常 30～60 秒就可以讲清楚，而且完整度很高。

---

# 九、把整场面试串成一个完整系统

一套比较完整的自动退款系统可以设计为：

```text
用户提交退款
      ↓
退款资格校验
      ↓
基础风控规则
      ↓
风险评分
  ↓          ↓
自动退款     人工审核
  ↓
创建 RefundOrder
生成唯一 refund_id
  ↓
数据库唯一约束
  ↓
REFUND_PROCESSING
  ↓
调用支付网关
  ↓
┌──────────┬──────────┬──────────┐
成功        明确失败       超时
↓           ↓             ↓
SUCCESS     FAILED        UNKNOWN
                            ↓
                         主动查单
                            ↓
                    SUCCESS / FAILED
```

后台再增加：

```text
退款系统数据库
      ↕
支付渠道账单
      ↓
每日 / 月度对账
      ↓
差异单
      ↓
自动修复 / 人工处理
```

整个系统最终解决的是四件事：

1. **哪些人可以自动退款；**
2. **一笔退款当前处于什么状态；**
3. **无论用户怎么重试，都不能多退钱；**
4. **即使系统发生异常，最终也能通过查单和对账恢复正确状态。**

# 十一、这类题的通用答题模板

以后再遇到支付、订单、退款、库存等场景题，可以先从五个问题展开：

```text
1. 业务规则是什么？
2. 状态怎么流转？
3. 怎么保证不会重复执行？
4. 异常情况下怎么恢复？
5. 最终怎么确认系统里的数据和真实世界一致？
```

对应技术概念：

```text
业务规则
   ↓
状态机
   ↓
幂等
   ↓
重试 / 查单 / 补偿
   ↓
对账
```

这套思路不仅适用于退款，也适用于：

- 支付；
- 订单；
- 库存扣减；
- 优惠券核销；
- 转账；
- 充值；
- 提现；
- 售后；
- 结算系统。

# 十二、一句话复盘

这次面试的主要问题不是思路完全错误，而是：

> **能够想到“做什么”，但对“资金系统如何保证正确性”的工程细节还不够完整。**

后续重点提升：

**业务不变量 → 状态机 → 幂等 → 超时查单 → 最终一致性 → 对账**

把这条链路吃透以后，同类后端系统设计题的回答质量会提升非常明显。
